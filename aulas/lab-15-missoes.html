Antes de começar

Seu sistema tem vários serviços. Hoje você aprende a enxergar a jornada de uma requisição e descobrir onde o tempo é gasto — sem adivinhação.

Pré-requisitos

  • Python 3.12 com fastapi, uvicorn e httpx.
  • Os pacotes do OpenTelemetry: pip install opentelemetry-distro opentelemetry-instrumentation-fastapi opentelemetry-exporter-otlp (a Missão 2 detalha).
  • O exemplo da aula: aulas/exemplos/aula15/tracing_demo.py. Para a Missão 3, Docker (para subir o Jaeger).
  • Reaproveite o gateway/ + inferencia/ da Aula 14 como fluxo a instrumentar.

Regra de ouro: peça ajuda — e registre

Pode usar docs, colegas e IA; registre no PROMPTS.md o que usou e o que fez com a resposta.

📒 Obrigatório — PROMPTS.md. Fonte · pergunta · resumo · o que você fez. Não vale colar o que não entende.

Missão 1 — Ler um trace entender ~15 min

Objetivo: entender span, trace e cascata (waterfall) antes de instrumentar código real.

cd exemplos/aula15
python tracing_demo.py        # imprime a cascata e aponta a etapa mais lenta

Edite as durações no final do arquivo (ex.: faça a recuperacao ficar mais lenta que a geracao) e rode de novo: o gargalo apontado deve mudar.

  • rodei e li a cascata (quem é pai/filho de quem)
  • mudei as durações e o gargalo apontado mudou
  • sei dizer o que é span, trace e trace_id

🧭 Travou? Releia o slide "Rastreamento distribuído". IA (registre): "O que é um span e como vários spans formam um trace? O que o trace_id tem a ver com isso?"

✅ Entregável. Sua versão do tracing_demo.py com outro gargalo + uma frase explicando a cascata.

Missão 2 — Instrumentar com OpenTelemetry instrumentar ~25 min

Objetivo: gerar traces a partir de código real (o gateway + a inferência da Aula 14), com exportação para o console primeiro.

Passo 1 — instale e rode com a instrumentação automática

pip install opentelemetry-distro opentelemetry-instrumentation-fastapi
opentelemetry-bootstrap -a install
# exporta os spans para o console (sem backend ainda):
opentelemetry-instrument --traces_exporter console uvicorn app:app --app-dir inferencia --port 8001

Faça algumas requisições e veja os spans aparecerem no console (nome, duração, trace_id).

Passo 2 — propague o contexto entre serviços

Instrumente também o gateway e o cliente HTTP (opentelemetry-instrumentation-httpx). Assim o trace_id do gateway continua na inferência — um único trace cobre os dois serviços.

  • spans aparecendo no console (inferência)
  • gateway instrumentado e chamando a inferência
  • o mesmo trace_id aparece nos dois serviços

🧭 Travou? Não aparece nada? Confirme que rodou via opentelemetry-instrument. IA (registre): "Como o OpenTelemetry propaga o contexto de trace entre dois serviços FastAPI por HTTP?"

✅ Entregável. Saída do console mostrando spans dos dois serviços com o mesmo trace_id.

Missão 3 — Visualizar os traces (Jaeger) visualizar ~20 min

Objetivo: ver a cascata visual num visualizador de verdade.

# sobe o Jaeger (tudo-em-um) com interface em http://localhost:16686
docker run -d --name jaeger -p 16686:16686 -p 4317:4317 jaegertracing/all-in-one:latest
# aponte o exporter OTLP para o Jaeger e rode os servicos:
# set OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 (e --traces_exporter otlp)

Gere requisições, abra localhost:16686, escolha o serviço e veja o trace em cascata. Ache a barra mais longa.

  • Jaeger no ar (16686)
  • traces chegando (vejo a cascata)
  • identifiquei visualmente a etapa mais lenta

🧭 Travou? Nada no Jaeger? Confirme a porta 4317 (OTLP gRPC) e o OTEL_EXPORTER_OTLP_ENDPOINT. IA (registre): "Qual a diferenca entre exportar traces para o console e para um backend OTLP como o Jaeger?"

✅ Entregável. Um print da cascata no Jaeger com a etapa mais lenta destacada.

Missão 4 — Instrumentar o C3.A2 e achar o gargalo entregar ~15 min

Objetivo: aplicar tudo ao projeto e produzir a análise do gargalo.

  1. Instrumente o fluxo do RAG (gateway → recuperação → geração) com OpenTelemetry.
  2. Colete um trace de ponta a ponta de uma pergunta e salve a imagem.
  3. Escreva a análise: qual é a etapa mais lenta e o que você faria (ex.: cache, timeout, modelo menor).
  • C3.A2 instrumentado (trace cobre os serviços do fluxo)
  • imagem do rastreamento salva no repositório
  • análise do gargalo escrita

✅ Entregável. Projeto instrumentado + imagem do trace + análise do gargalo.

Desafios — para quem voar 🚀

  • Span manual: crie um span customizado em torno de um trecho específico (ex.: só a montagem do prompt) para medi-lo separadamente.
  • Atributos no span: anexe atributos úteis (tamanho do texto, modelo usado) e filtre por eles no Jaeger.
  • Erro no trace: force uma falha na geração e veja o span marcado como erro na cascata — observabilidade também mostra o que quebrou, não só o que demorou.
