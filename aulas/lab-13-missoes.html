Antes de começar

Você vai pegar um serviço que roda na sua máquina e empacotá-lo num container, para então publicá-lo numa nuvem gratuita. A peça nova é o Dockerfile — a receita que descreve a imagem.

Pré-requisitos

  • Docker instalado e o daemon rodando (abra o Docker Desktop; docker ps deve responder sem erro).
  • Python 3.12 com fastapi e uvicorn (para rodar local antes de conteinerizar).
  • Uma conta grátis em Render ou Railway (free tier) para a Missão 3.
  • O exemplo da aula: aulas/exemplos/aula13/ (app.py, Dockerfile, requirements.txt, .dockerignore).

💡 Por que esse exemplo. O app.py devolve o hostname. Local, é o nome do seu PC; no container, é o ID do container. Isso deixa visível qual instância respondeu — essencial quando o serviço escalar.

Regra de ouro: peça ajuda — e registre

Você pode e deve buscar ajuda (docs, colegas, IA). A exigência é rastreabilidade: registre no PROMPTS.md o que usou e o que fez com a resposta.

📒 Obrigatório — PROMPTS.md no seu repositório. Fonte · o que perguntou · resumo da resposta · o que você fez com ela. Não vale colar o que não entende.

Missão 1 — Rodar o serviço local entender ~15 min

Objetivo: ver o serviço funcionando antes de conteinerizar (assim você sabe que o problema, se houver, é do container, não do código).

cd exemplos/aula13
uvicorn app:app --reload --port 8000     # abra http://127.0.0.1:8000
# GET /        -> {"mensagem":"Ola da nuvem!","host":"<seu-pc>","versao":"1.0"}
# GET /health  -> {"status":"ok"}     GET /docs -> Swagger
  • / responde com o host (nome do seu PC) e a versão
  • /health responde {"status":"ok"}
  • o /docs abre

🧭 Travou? Faltou dependência? pip install fastapi "uvicorn[standard]". IA (registre): "Para que serve o endpoint /health num serviço que vai para a nuvem?"

✅ Entregável. O serviço rodando local, commitado no seu repositório.

Missão 2 — Conteinerizar (build + run) construir ~20 min

Objetivo: empacotar o serviço numa imagem e rodá-lo isolado — e ver o host mudar para o ID do container.

docker build -t servico-nuvem .          # le o Dockerfile e monta a imagem
docker run -p 8000:8000 servico-nuvem    # roda; -p liga a porta sua -> do container
# acesse http://127.0.0.1:8000 : o "host" agora e o ID do container
docker ps                                 # veja o container rodando

Entenda o Dockerfile (linha a linha)

  • FROM python:3.12-slim — base enxuta com Python.
  • COPY requirements.txt + RUN pip install antes do código — aproveita o cache de camadas (muda o código, não reinstala tudo).
  • CMD [... "--host","0.0.0.0" ...] — ouvir em 0.0.0.0, senão ninguém de fora do container acessa.
  • docker build terminou sem erro
  • docker run -p 8000:8000 e o serviço respondeu no navegador
  • o host no JSON mudou (virou o ID do container)

🧭 Travou? "Cannot connect to the Docker daemon" = o Docker Desktop não está aberto. Porta ocupada? pare o uvicorn local da Missão 1. IA (registre): "Por que, no Dockerfile, copiar o requirements.txt e instalar as dependências antes de copiar o código aproveita melhor o cache?"

✅ Entregável. O Dockerfile no repositório + um print do serviço respondendo de dentro do container (host = ID do container).

Missão 3 — Publicar na nuvem (URL pública) deploy ~20 min

Objetivo: colocar o serviço no ar, acessível por qualquer pessoa, numa nuvem gratuita.

  1. Suba o código (com o Dockerfile) para um repositório no GitHub.
  2. No Render (ou Railway): New → Web Service → conecte o repositório → ele detecta o Dockerfile → Deploy.
  3. Configure a porta/health check se pedir (/health) e aguarde o build terminar.
  4. Acesse a URL pública gerada e confirme o JSON de /.

💡 Free tier "dorme". No plano gratuito, o serviço pode hibernar por inatividade e a primeira requisição demora alguns segundos (cold start — lembra da Aula 6?). É esperado.

  • código + Dockerfile no GitHub
  • deploy concluído no Render/Railway
  • a URL pública responde o JSON de /

🧭 Travou? Build falhou? Leia o log do deploy (quase sempre diz a dependência faltante). Porta errada? a nuvem costuma injetar a porta via variável PORT — ajuste o CMD/start se o provedor pedir. IA (registre): "Como o Render decide a porta que meu container deve escutar e o que e a variavel PORT?"

✅ Entregável. A URL pública do serviço no ar (anote no README).

Missão 4 — Lançar o C3.A2 entregar ~15 min

Objetivo: começar o projeto integrador conteinerizando seus serviços — um Dockerfile por serviço.

  1. No projeto do C3.A2, escolha o serviço mais simples e escreva o Dockerfile dele (use o desta aula como modelo).
  2. docker build de cada serviço, confirmando que todos buildam individualmente.
  3. Anote no README o comando de build/run de cada serviço.
  • um Dockerfile por serviço do C3.A2
  • cada serviço builda individualmente
  • README com os comandos de build/run

✅ Entregável. Repositório do C3.A2 com todos os serviços conteinerizados (buildando). Subir tudo junto fica para a Aula 14.

Desafios — para quem voar 🚀

  • Imagem menor: compare o tamanho da imagem (docker images) antes e depois de um .dockerignore caprichado e de um FROM ...-slim. Quanto você economizou?
  • Variável de ambiente: rode docker run -e APP_VERSION=2.0 -p 8000:8000 servico-nuvem e veja a versão mudar na resposta — sem reconstruir a imagem.
  • Duas réplicas: rode dois containers em portas diferentes (-p 8000 e -p 8001) e veja o host diferente em cada um — a prévia da escala da próxima aula.
