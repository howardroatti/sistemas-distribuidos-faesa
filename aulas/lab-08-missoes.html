Antes de começar

Você vai transformar o serviço síncrono da Aula 6 em um pipeline assíncrono: quem pede não espera — entrega a tarefa, recebe um id e busca o resultado depois. A peça nova é a fila (Redis) com um worker processando em segundo plano.

Pré-requisitos

  • Kit da C1 clonado: git clone https://github.com/howardroatti/sd-2026-2-kit-c1a2.git
  • Ambiente Python (venv) ativo dentro do kit e dependências instaladas (pip install -r requirements.txt). Se a ativação do venv barrar no PowerShell com "running scripts is disabled", rode uma vez: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned (responda S).
  • Docker funcionando (para subir o Redis).
  • Você vai precisar de 3 a 4 terminais abertos (Redis, API, worker(s), e um para comandos).

💡 O ponto de partida. No kit, o assíncrono ainda não existe: as rotas POST /predict e GET /resultado/{id} e o "guardar resultado" do worker vêm como TAREFAS (trechos comentados que levantam NotImplementedError). Os auxiliares de fila (app/fila.py) já estão prontos — você só precisa ligá-los. Tudo está descrito no TAREFAS.md do kit.

Regra de ouro: peça ajuda — e registre

Travar faz parte. Você pode e deve buscar ajuda: documentação oficial, colegas, e também uma IA (LLM). A única exigência é rastreabilidade: registre o que você usou. Isso vale nota como evidência de processo e treina uma competência real de engenharia — usar ferramentas com discernimento.

📒 Obrigatório — arquivo PROMPTS.md no seu repositório. Sempre que uma fonte externa (docs, vídeo, colega) ou uma IA te ajudar, anote. O que não vale: colar código que você não entende. O que vale: usar a ajuda para entender e então escrever/ajustar você mesmo.

Missão 1 — Construir a fila construir ~25 min

Objetivo: fazer o pipeline assíncrono funcionar de ponta a ponta — POST /predict enfileira e devolve um id; um worker processa; GET /resultado/{id} devolve o resultado pronto.

Passo 1 — suba o Redis e a API

cd sd-2026-2-kit-c1a2          # aqui está o docker-compose.yml
docker compose up -d           # sobe o Redis em segundo plano
docker compose ps              # confira: o serviço redis deve estar "running/healthy"

# terminal 2 (com o .venv ativo):
uvicorn app.api_rest:app --reload --port 8000     # abra http://127.0.0.1:8000/docs

📁 Diretório certo. O docker compose precisa rodar na raiz do kit (onde está o docker-compose.yml). Erro "no configuration file provided" = você está na pasta errada.

Passo 2 — implemente as 3 TAREFAS

Abra os arquivos, ache os blocos marcados como TAREFA (comentados) e implemente. Você não mexe no Redis diretamente — usa os auxiliares prontos de app/fila.py.

  • TAREFA 1 — em app/api_rest.py: rota POST /predict que recebe {texto}, chama fila.enfileirar(texto) e devolve {"id": ...} com status 202 (não espera o processamento).
  • TAREFA 2 — em app/api_rest.py: rota GET /resultado/{id} que chama fila.buscar_resultado(id); se não existir, responde 404.
  • TAREFA 3 — em app/worker.py: depois de modelo.prever(...), chame fila.guardar_resultado(tarefa["id"], resultado) (e remova o raise NotImplementedError).

Passo 3 — suba o worker e valide

# terminal 3 (com o .venv ativo):
python -m app.worker           # deve imprimir "carregando modelo..." e "aguardando tarefas"

No /docs (Swagger), teste o fluxo: POST /predict com um texto → copie o id → GET /resultado/{id} → o status deve virar "pronto".

  • docker compose ps mostra o Redis no ar
  • /docs abre e mostra as rotas /predict e /resultado/{id}
  • POST /predict devolve um id na hora (status 202)
  • o worker imprime "processando <id>"
  • GET /resultado/{id} retorna status: "pronto"

🧭 Travou? Pesquise:

  • FastAPI — Request Body, Status Code, Path Parameters, Erros/404.
  • Leia o TAREFAS.md do kit e as DICAS comentadas nos próprios arquivos.
  • IA (registre no PROMPTS.md): "No FastAPI, como declaro status_code=202 numa rota POST e como leio um parâmetro de caminho {id}? Explique o conceito, não me dê a solução pronta."

✅ Entregável. Pipeline assíncrono funcionando: um POST /predict vira um id e o GET /resultado/{id} retorna pronto. Faça commit das TAREFAS 1, 2 e 3.

Missão 2 — Redis por dentro + meça a escala medir ~15 min

Objetivo: deixar de tratar o Redis como caixa-preta (ver a fila de verdade) e medir o efeito de adicionar workers.

Passo 1 — espie a fila

docker compose exec redis redis-cli    # abre o cliente do Redis
> MONITOR            # dispare um POST noutro terminal e veja RPUSH tarefas / SET resultado:...
> LLEN tarefas       # quantas tarefas estão esperando na fila
> LRANGE tarefas 0 -1 # o conteúdo da fila
> KEYS resultado:*   # os resultados já guardados
> GET resultado:<id> # o resultado de uma tarefa

Saia do MONITOR com Ctrl+C e do cliente com exit.

Passo 2 — meça a vazão variando os workers

Com a API no ar, suba 1 worker e rode a carga. Depois repita com 3 e 6 workers (cada worker no seu terminal), sempre anotando o tempo.

python exemplos/aula08/carga.py 50     # dispara 50 tarefas e cronometra até todas ficarem prontas
nº de workerstempo total (s)tarefas/s
1??
3??
6??

💡 Reflita. Dobrar os workers não dobra a vazão para sempre. Em algum ponto o gargalo deixa de ser "quantos processam" e vira a CPU / o modelo. Onde a sua curva parou de crescer? Esse é o seu ponto de saturação.

  • vi no MONITOR os comandos RPUSH tarefas e SET resultado:...
  • rodei carga.py com 1, 3 e 6 workers
  • preenchi a tabela e identifiquei o ponto de saturação

🧭 Travou? Referências: comandos de lista do Redis (LLEN, LRANGE); medir tempo em Python com time.perf_counter(). IA (registre): "Como interpretar uma curva de vazão que cresce e depois estabiliza ao aumentar o número de workers? O que é ponto de saturação?"

✅ Entregável. A tabela de vazão (1/3/6 workers) salva no repositório, por exemplo num relatorio.md.

Missão 3 — Quebrar e observar resiliência ~15 min

Objetivo: sentir na prática a falha parcial e a durabilidade — o que a fila protege e o que ela não protege.

Experimentos

  1. Derrube o worker (Ctrl+C) no meio de uma carga. Rode LLEN tarefas: o número cresce — a fila segura o trabalho. Suba o worker de novo e veja a fila drenar.
  2. Derrube o Redis: docker compose stop redis. Agora um POST /predict falha ao tentar enfileirar — sem fila, não há assíncrono. Religue: docker compose start redis.
  3. Dead-letter (TAREFA 5): faça o worker, ao dar erro numa tarefa, reprocessar até N vezes e, persistindo a falha, mandar a mensagem para uma lista dead_letter — igual ao fila_demo.py do aquecimento.

💡 Como provocar um erro de propósito. O modelo quase nunca falha sozinho. Para testar a dead-letter, trate um texto especial como falha no worker (ex.: se o texto for "ENVENENADA", raise) — exatamente a técnica do fila_demo.py.

  • vi a fila crescer com o worker derrubado e drenar ao voltar
  • vi o POST /predict falhar com o Redis parado
  • implementei retentativa + dead_letter no worker (TAREFA 5)

🧭 Travou? Revisite o fila_demo.py (aquecimento) — a lógica de retentativa e dead-letter está toda lá, em memória. Você vai portá-la para o worker do kit usando o cliente do Redis. IA (registre): "Explique o padrão retry + dead-letter queue e como eu contaria as tentativas de uma mensagem antes de descartá-la."

✅ Entregável. Worker com retentativa + dead-letter e uma anotação curta: quem sobrevive à queda de quem? (a fila protege contra picos e contra a queda do worker; o Redis, porém, é um ponto único — gancho para a Aula 10, CAP).

Desafios — para quem voar 🚀

Terminou as missões? Escolha um. Cada um vira um ponto forte no C1.A2/C2.A2 (e ótimo para o ENADE):

  • Pub/sub na unha: em 2 terminais abra docker compose exec redis redis-cli e rode SUBSCRIBE avisos; num 3º, PUBLISH avisos "pronto". Todos os assinantes recebem — na fila (RPUSH/BLPOP), só um pegava. É a diferença fila × pub/sub, na mão.
  • Latência p50/p95: meça o tempo de cada GET /resultado/{id} e calcule os percentis (não só a média). Por que a média engana?
  • Gateway mínimo: um FastAPI que roteia /infer → serviço, com um contador de rate limit e um header de auth fake. É a ponte para a segurança (C3).
